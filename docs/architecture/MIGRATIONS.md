# Database Migrations

AdvanCore uses [Alembic](https://alembic.sqlalchemy.org/) to version and apply
PostgreSQL schema changes. This replaces the previous approach of relying solely
on `Base.metadata.create_all()`.

## Configuration

- `alembic.ini` — Alembic settings. The `sqlalchemy.url` placeholder is
  intentionally left empty; the real `DATABASE_URL` is read from the
  environment (and `.env` in development) by `alembic/env.py`.
- `alembic/env.py` — Alembic environment bootstrap. Imports
  `advancore.models.Base` and sets `target_metadata = Base.metadata` so
  autogenerate can discover model changes.
- `alembic/versions/` — Migration revision scripts.

## Workflow

### 1. Create a new migration after changing models

```bash
.venv/bin/alembic revision --autogenerate -m "describe the change"
```

Review the generated file in `alembic/versions/` before committing. Never commit
unreviewed migrations.

### 2. Apply migrations

```bash
.venv/bin/alembic upgrade head
```

### 3. Check current state

```bash
.venv/bin/alembic current
.venv/bin/alembic history
```

### 4. Revert migrations (local/dev only)

```bash
.venv/bin/alembic downgrade -1
```

## Rules

- All schema changes must be implemented through migrations.
- Do not silently delete tables, columns, or relationships.
- Do not rewrite migration history after a revision has been applied to a
  shared database.
- Never commit database credentials. `DATABASE_URL` comes from the environment.
- Keep migrations small and reversible.
- Review autogenerated migrations for correctness; Alembic does not always
  detect every change (for example, renames are rendered as drop + add).

## Adopting an existing database

Databases that were created previously with `Base.metadata.create_all()` must
not blindly run `alembic upgrade head`, because the baseline migration will fail
when tables already exist.

Use this verified procedure instead:

1. **Verify schema parity** between the existing database and the baseline
   migration. Inspect tables, columns, primary keys, foreign keys, nullability,
   and important types (for example, by reflecting the schema with SQLAlchemy).
2. **Only if parity is confirmed**, stamp the database at the baseline revision:

   ```bash
   .venv/bin/alembic stamp head
   ```

3. **Confirm the stamp** with:

   ```bash
   .venv/bin/alembic current
   ```

   Expected output: `639d8b65223c (head)`.

4. **Apply migrations**:

   ```bash
   .venv/bin/alembic upgrade head
   ```

   Against a database already at the baseline, this should be a no-op and
   succeed.

### Warnings

- Never stamp a database whose schema parity has not been verified.
- Never use this procedure blindly on production.
- If parity checks fail, resolve the schema difference first; do not force or
  stamp the database.

## Baseline

The baseline revision (`alembic/versions/639d8b65223c_baseline.py`) creates the
initial AdvanCore tables: `projects`, `knowledge_items`, `activity_logs`, and
`system_settings`.
